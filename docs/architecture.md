## Design Philosophy

Basecamp is designed around three foundational principles:

1. **Zero Global Pollution**: Toolchains, compilers, formatters, and language servers must live inside isolated, per-project Nix development shells. No global language runtimes are required.
2. **Deterministic Reproducibility**: Environments generated by Basecamp pin their channel sources and dependencies, guaranteeing bit-for-bit identical developer environments across machines and operating systems.
3. **Decoupled Responsibilities**: Basecamp focuses strictly on developer environment provisioning (`flake.nix`, `.envrc`, `.gitignore`) and starter scaffolding. Domain-specific compilers and downstream tools (such as Snowpack for documents or Cargo for Rust) retain control over their domain models.

## The Lore

> **basecamp** (`/ˈbeɪs.kæmp/`) — *noun:* The primary staging outpost pitched at the foot of a glacier, stocking provisions, shelters, and technical climbing gear before an expedition pushes into unmapped arctic ice.

Software engineering stacks evolve continuously, introducing divergent dependencies, competing package managers, and inconsistent runtime libraries. In arctic expeditions, venturing onto uncharted glaciers without established base camps leads to isolation and logistical failure. 

Basecamp establishes an insulated outpost before any exploratory code is written. By locking down compiler versions, system libraries, and shell hooks into a hermetic Nix flake, developers can explore new technical terrain without risking host instability or unreproducible build errors.

## Execution Engine

The Basecamp execution pipeline operates in three sequential phases:

```
[CLI Invocation]
       │
       ▼
[Role & Target Resolution]
       ├── Builtin Registry (`BUILTIN_ROLES`)
       ├── User Config (`~/.config/basecamp/roles.toml`)
       └── Target Expansion (e.g., `snowpack:slides` -> `slides`)
       │
       ▼
[Environment Synthesis]
       ├── Channel Resolution (`resolve_nixpkgs_url`)
       ├── Runtime Library Injection (`LD_LIBRARY_PATH`)
       ├── Hook Aggregation
       └── Multi-Platform DevShell Generation (`flake.nix`, `.envrc`, `.gitignore`)
       │
       ▼
[Asset Scaffolding]
       ├── Overwrite Safety Verification
       ├── Template Parameterization
       └── Git Automatic Staging (`git add`)
```

### 1. Role Resolution

When commands like `basecamp init rust next ops` are invoked:
- The CLI parses canonical role identifiers and aliases (`rs` $\to$ `rust`, `ex` $\to$ `elixir`, `py` $\to$ `python`).
- Custom user roles loaded from `~/.config/basecamp/roles.toml` are merged into the registry.
- Target specifiers (e.g. `snowpack:slides` or `--mode slides`) are resolved against role target definitions.

### 2. Environment Synthesis

The environment generator (`basecamp.core.environment`) renders `flake.template`:
- Aggregates the unique union of Nix packages across all selected roles.
- Constructs shell activation hooks, formatting an informational banner showing active roles.
- Maps role-specific ignore patterns into `.gitignore` (such as `.direnv/`, `result`, `target/`, `.venv/`, `node_modules/`).
- Emits `.envrc` with `use flake` if direnv support is active.

### 3. Asset Scaffolding

The scaffolding engine (`basecamp.scaffold.engine`) provisions starter files:
- Inspects role template directories across package assets and user configuration paths.
- Copies foundation files (e.g. `pyproject.toml`, `Cargo.toml`, `CMakeLists.txt`) during `init` and `project` commands.
- Copies starter source files (e.g. `main.py`, `main.rs`, `main.zig`) during `init` and `new` commands.

## Safety Mechanisms

Basecamp includes defensive safeguards to prevent unintentional data loss:

### Overwrite Protection

Before writing any file to disk, Basecamp verifies whether the file already exists:
- If a target file exists, Basecamp displays a confirmation prompt:
  ```text
  File 'flake.nix' already exists. Overwrite? [y/N]
  ```
- In headless scripts or CI pipelines, pass `-f` or `--force` to intentionally overwrite without prompting.
- In dry-run mode (`-n` or `--dry-run`), no disk modifications occur; file contents are formatted directly to stdout.

### Atomic Git Staging

Nix Flakes strictly require tracked files to be known to Git. When generating files inside a Git repository:
- Basecamp automatically runs `git add <files>` after generation.
- If automatic Git staging is undesirable, pass `--no-git` to disable this behavior.

## C Runtime Injection

Many dynamic language runtimes (such as Python wheels, Node native addons, and Julia libraries) require access to host C libraries that are not packaged in standard locations on Nix-based systems.

To eliminate `libstdc++.so.6: cannot open shared object file` and related linking failures, Basecamp automatically configures dynamic linker paths in generated development shells:

```nix
shellHook = ''
  export LD_LIBRARY_PATH="${lib.makeLibraryPath runtimeLibs}:$LD_LIBRARY_PATH"
'';
```

The standard library bundle injected into `runtimeLibs` includes:
- `stdenv.cc.cc.lib` (C/C++ standard runtime)
- `zlib` (Compression library)
- `glib` (Core application building blocks)
- `libxml2` (XML parsing engine)
- `openssl` (Cryptographic routines and SSL/TLS)
- `libffi` (Foreign function interface library)
